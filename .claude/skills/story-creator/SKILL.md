# 物語作成スキル（story-creator）

ユーザーから「最初」と「結末」を受け取り、8つのフェーズを順に進めて物語を完成させる。各フェーズで成果物（Markdownファイル）を作り、**ユーザーの承認を得てから次へ進む**。

## なぜ承認ゲートが重要か

後のフェーズは前のフェーズの成果物を土台にする。たとえば相関図が曖昧なまま章ごとの起承転結を書くと、肉付けの段階で人物関係の矛盾が表面化し、書き直しが連鎖する。小さな食い違いを早い段階でユーザーに潰してもらうことが、結果的に最も速く、ユーザーの意図に近い物語になる。だからフェーズをまたいで先走らない。

## インプット

| 項目 | 必須 | 内容 |
|---|---|---|
| 最初 | ○ | 物語の冒頭の状況・場面・一文など |
| 結末 | ○ | 物語がどう終わるか（ハッピー/バッド、最後の場面、到達点など） |
| 補足 | 任意 | ジャンル、想定の長さ（章数・文字数）、トーン、読者層、NG要素など |

最初か結末のどちらかが欠けている場合は、先に進む前に聞く。補足は一度だけまとめて尋ね、「特になし」でも構わないと伝える（質問攻めにしない）。最初・結末が曖昧でも、フェーズ1でアイデアを出す過程で具体化できるので、曖昧さ自体は止める理由にならない。

## モードの選択（通常／長編）

| モード | 目安の長さ | 構造 | 手順 |
|---|---|---|---|
| 通常 | 約10万字まで（短編・中編） | 章 | このファイルの手順 |
| 長編 | 約10万字を超える（50万字級など） | 部 → 章 → 節 | **まず `references/long-form.md` を読む。** 部ごとに構成を決めて承認する流れ、承認の粒度、`story-state.md`（物語の現在地）の運用が、通常と異なる |

長さの希望（補足）から判断する。迷ったら、想定の規模（総字数・部の数）をユーザーに尋ねて決める。長編モードでは、このファイルの「承認ゲートの進め方」「上流の成果物を直す必要が出たとき」「品質の基本姿勢」はそのまま守り、**手順・ファイル構成・承認の粒度で異なる点は `long-form.md` を優先する**。以降の説明は、通常モードのもの。

## 手順の全体像

| # | フェーズ | 成果物 |
|---|---|---|
| 1 | アイデア出し | `01_ideas.md` |
| 2 | 全体の章構成 | `02_chapter-outline.md` |
| 3 | 登場人物の整理 | `03_characters.md` |
| 4 | 相関関係図 | `04_relationships.md` |
| 5 | 重要な物の整理 | `05_key-items.md` |
| 6 | 章ごとの起承転結 | `06_chapter-plots/chNN.md`（章ごと） |
| 7 | 章ごとの肉付け | `07_chapters/chNN.md`（章ごと） |
| 8 | 全体レビュー | `08_review.md`、完成稿 `09_manuscript.md` |

各フェーズでやること、品質の観点、つまずきやすい点は `references/phase-guides.md` にある。Gitの運用（サブモジュール登録、承認ごとのコミット）は `references/git-workflow.md` にある。**そのフェーズに入るとき、該当セクションを読んでから作業する**（全部を最初に読む必要はない）。

## 成果物のディレクトリ構成

作業ディレクトリ直下の `stories/<物語名>/` に作る。物語名は仮タイトルでよい（ユーザーに聞くか、最初と結末から提案する。後から変えられる）。

```
stories/<物語名>/
├── progress.md                  # 進捗・インプット・執筆方針・変更履歴（常に最新に保つ）
├── 01_ideas.md
├── 02_chapter-outline.md
├── 03_characters.md
├── 04_relationships.md
├── 05_key-items.md
├── 06_chapter-plots/
│   ├── ch01.md
│   └── ch02.md ...
├── 07_chapters/
│   ├── ch01.md
│   └── ch02.md ...
├── 08_review.md
└── 09_manuscript.md             # 承認済みの全章を結合した完成稿
```

各ファイルのフォーマットは `assets/templates/` のテンプレートに従う。ファイルを作るときは対応するテンプレートを読み、見出し構成を崩さずに埋める。フォーマットを揃えておくと、ユーザーがレビューしやすく、後続フェーズが前の成果物を機械的に参照しやすくなる。

| 成果物 | テンプレート |
|---|---|
| `progress.md` | `assets/templates/progress.md` |
| `01_ideas.md` | `assets/templates/01_ideas.md` |
| `02_chapter-outline.md` | `assets/templates/02_chapter-outline.md` |
| `03_characters.md` | `assets/templates/03_characters.md` |
| `04_relationships.md` | `assets/templates/04_relationships.md` |
| `05_key-items.md` | `assets/templates/05_key-items.md` |
| `06_chapter-plots/chNN.md` | `assets/templates/06_chapter-plot.md` |
| `07_chapters/chNN.md` | `assets/templates/07_chapter-draft.md` |
| `08_review.md` | `assets/templates/08_review.md` |

## Git管理

`stories/<物語名>/` は物語ごとに独立したGitリポジトリで、このスキルのリポジトリからはサブモジュールとして参照される。スキルの改善履歴と物語の執筆履歴を混ぜず、物語単位で公開・共有できるようにするため。新規物語のセットアップ手順、承認ごとのコミット、コミットメッセージの形式は `references/git-workflow.md` に従う。要点は次のとおり。

- 新しい物語を始めるときに、子リポジトリの初期化とサブモジュール登録を行う（リモートURLはユーザーに聞く）。
- ユーザーの承認が出るたびに、子リポジトリへコミットする。承認前の修正中はコミットしない。
- pushはしない。

## 開始時の動き

1. `stories/` 配下に既存の物語があり `progress.md` があれば、新規作成か続きから再開かをユーザーに確認する。再開する場合は `progress.md` を読み、「承認済み」の最後のフェーズの次から始める（長編モードなら、`progress.md` の「部の進捗」と `story-state.md` を読み、承認済みの最後の位置の次から始める）。`stories/<物語名>/` が空なら、サブモジュールが未取得なので `references/git-workflow.md` の再開手順を行う。
2. 新規なら、インプット（最初・結末・補足）を確認し、長さの希望から通常モードか長編モードかを決める。`stories/<物語名>/progress.md` をテンプレートから作ってインプットを記録する（長編モードは `progress-long.md` から作り、「モード：長編」と想定の規模も記録する）。続けて `references/git-workflow.md` の手順で、子リポジトリの初期化とサブモジュール登録を行う。
3. フェーズ1に入る。

## 承認ゲートの進め方（全フェーズ共通）

1. **成果物をファイルに書く。** 状態は `progress.md` で「レビュー待ち」にする。
2. **ユーザーに提示する。** ファイルパスと要点を伝える。全文はファイルで読めるので、チャットには要点と「ここを判断してほしい」という論点を絞って書く。そのうえでフィードバックを求め、問題なければ承認してほしいと伝える。ワークスペースの `viewer/start.cmd` を起動すると、進捗と成果物をブラウザで整形表示できる（レビュー待ちの一覧つき。承認前の変更は、前回承認からの差分で読める）。最初の提示のときに一度だけ案内する。
3. **返答を待つ。** 同じターンで次のフェーズに進まない。
4. **返答を読み分ける。**
   - 「OK」「承認」「次へ」など承認が明確 → 5へ。
   - 「いいけど、ここは〜」のように修正要望を含む → 承認ではなく修正依頼として扱う。
   - どちらか判断できない → 承認なのか修正なのかを短く確認する。
5. **修正依頼なら**、ファイルを直して再提示し、3へ戻る。承認が出るまで繰り返す。
6. **承認されたら**、`progress.md` の状態を「承認済み」にして日付を入れ、成果物リポジトリへコミットしてから（`references/git-workflow.md`）、次のフェーズへ進む。

フェーズ6と7は章ごとの成果物になる。

- フェーズ6：全章分をまとめて提示し、フェーズ全体として承認をもらう（章どうしのつながりを一覧して判断してもらうほうが確認しやすいため）。
- フェーズ7：1章ずつ提示して、その章ごとに承認をもらう。本文は長く、序盤章へのフィードバック（文体、テンポ、人物の話し方）が後続章に影響するため。

## 上流の成果物を直す必要が出たとき

後のフェーズで、承認済みの成果物に手を入れたくなることは普通に起こる（例：章の肉付け中に人物の口癖が決まった、起承転結を書いていたら章構成を入れ替えたくなった）。

- **情報の追加**（人物の背景、口癖、アイテムの来歴など）：該当ファイルの「追加情報」に、追加したフェーズ名を添えて追記する。人物の追加情報は特にこの形で蓄積する（`03_characters.md` の追加情報表）。
- **既存内容の変更**：ユーザーに変更の理由と影響範囲を伝え、了承を得てから直す。
- どちらの場合も `progress.md` の「変更履歴」に記録し、すでに承認済みの下流の成果物と矛盾しないか確認する。矛盾があればユーザーに報告して一緒に直す。
- 修正したら、承認ゲートのコミットとは別に、修正だけの単独コミットを作る（`references/git-workflow.md`）。

## 品質の基本姿勢

- **最初と結末は動かさない。** ユーザーが与えた条件なので、ユーザー自身が変更を申し出ない限り、構成・起承転結・本文のすべてで最初から結末へ確実に到達させる。
- **承認済みの内容を黙って変えない。** 変えるときは必ず上記の手順で。
- **不明点は作り込まずに尋ねる。** ただし1フェーズあたりの質問は、判断が分かれる重要なものに絞る。ささいな点は提案として成果物に入れ、フィードバックで直してもらう。
- **人物は台詞で魅力を見せる。** 性格・背景・関係に合わせて台詞を書き分け、固く説明的な台詞にしない。人物ごとの「声」はフェーズ3で設計し（`references/phase-guides.md` のフェーズ3）、フェーズ7で台詞に落とす（同「台詞の書き方」）。最初の章から、人間味のある台詞を書く。
